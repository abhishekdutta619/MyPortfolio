The drag-and-drop board in this site's KanbanFlow case study isn't wired up with react-dnd, dnd-kit, or any other library. It's about 60 lines of the native HTML5 drag-and-drop API and a bit of React state. That was a deliberate choice, not a shortcut — and it's worth being honest about what you get and what you give up.

## What the native API actually looks like

Three event handlers do all the work:

```tsx
<div draggable onDragStart={() => setDragging({ id: task.id, from: columnKey })}>
  {task.text}
</div>

<div
  onDragOver={(e) => e.preventDefault()} // required, or onDrop never fires
  onDrop={() => handleDrop(columnKey)}
>
  {/* column contents */}
</div>
```

`onDragOver` calling `preventDefault()` trips people up the first time — without it, the browser's default behavior is to reject the drop entirely. Once that's in place, the rest is just state: track which item is being dragged and where it came from, then move it on drop.

## Why not just reach for a library

For a lot of production kanban boards, I would. Libraries like dnd-kit solve real problems this approach doesn't touch: touch-device support that actually feels good, sortable reordering *within* a column (not just moving between columns), and — the big one — keyboard accessibility.

But for a self-contained demo whose entire job is to illustrate a state-management pattern, pulling in a drag-and-drop library is arguably solving a problem the demo doesn't have, at the cost of a dependency someone reading the code now has to understand too. The native API, for this specific case, is more legible, not less capable-for-purpose.

## The part I won't paper over

The demo on this site is **not keyboard-operable**. That's a real accessibility gap, and it's called out directly in the component's code comments rather than left for someone to discover. Full accessible drag-and-drop — arrow-key reordering, `aria-live` announcements when an item moves — is a legitimate feature, not a quick addition, and it's exactly the kind of thing a library like dnd-kit gets right that a hand-rolled version usually doesn't, unless you deliberately build it.

The lesson isn't "avoid libraries." It's that every dependency decision is really a decision about which problems you're choosing to solve yourself, and which you're borrowing a solution for — and that choice should be visible, not assumed.
