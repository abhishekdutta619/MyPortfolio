The publish-pipeline demo in this site's Simply Dwell Design case study isn't wired up with framer-motion, react-spring, or a state machine library like xstate. It's a stage index, a `setTimeout` chain, and a cleanup function. That was a deliberate choice, not a shortcut — and it's worth being honest about what you get and what you give up.

## What the sequencing actually looks like

One recursive `setTimeout` does all the work:

```tsx
function runPipeline() {
  if (running) return;
  setRunning(true);
  setActiveIndex(0);

  let i = 0;
  const step = () => {
    i += 1;
    if (i < stages.length) {
      setActiveIndex(i);
      timeoutRef.current = setTimeout(step, STEP_DELAY_MS);
    } else {
      setRunning(false);
    }
  };
  timeoutRef.current = setTimeout(step, STEP_DELAY_MS);
}
```

The part that's easy to get wrong: the timeout has to be cleared on unmount, or a component that's already gone can still try to call `setState` a beat later. A `useEffect` with a cleanup function that calls `clearTimeout` on whatever's currently in the ref handles it.

## Why not just reach for a library

For anything with more than one animated property, or anything that needs to interrupt and reverse mid-sequence, I would. Framer Motion's orchestration and stagger primitives solve real problems this approach doesn't touch — springs, gesture-driven interruption, exit animations that actually wait for each other.

But for a self-contained demo whose entire job is to illustrate a linear pipeline — draft, auth, function, commit, rebuild, live — pulling in an animation library is arguably solving a problem the demo doesn't have. Six sequential `setState` calls are more legible to someone reading the component for the first time than a dependency's config API, for this specific case.

## The part I won't paper over

The demo on this site can't be stopped once it's running — the "Publish" button just disables itself until the sequence finishes. There's no cancel, no interrupt, no way to jump ahead. That's a real, deliberate limitation for a demo, not an oversight, but it's the kind of shortcut that would be a genuine bug in anything real: a user who changes their mind mid-action needs an escape hatch, and this doesn't have one.

The lesson isn't "avoid libraries." It's that every dependency decision is really a decision about which problems you're choosing to solve yourself, and which you're borrowing a solution for — and that choice should be visible, not assumed.
